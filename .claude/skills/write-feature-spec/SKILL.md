# 기능 스펙 작성법

## 절차

1. **번호와 폴더**: 새 기능이면 `features.md`의 다음 번호로 `specs/NNN-영문-kebab/spec.md`를 만들고 `specs/_templates/spec.md`를 복사한다.
2. **근거 정리**: 화면(피그마 프레임 이름), 기획 메모, 결정 사항을 목록으로 만든다. 근거 없는 내용은 쓰지 않는다.
3. **배경과 목적**: 사용자가 얻는 것을 2~3줄로.
4. **사용자 시나리오**: 화면에서 하는 행동을 순서대로. 기술 용어 없이.
5. **요구사항 (FR)**: 시스템이 해야 하는 일. 한 FR에 한 가지.
6. **인수 조건 (AC)**: 아래 규칙.
7. **범위 밖**: 화면에 없거나 이번에 안 하는 것. 다음 후보면 "(후보)".
8. **열린 질문**: 결정이 필요한 것. 체크박스로.
9. **동기화**: `features.md` 표(링크·상태), 새 용어는 `glossary.md`.

## 인수 조건 쓰는 법

AC 하나 = 테스트 하나로 검증 가능한 크기. 구현 단계에서 테스트 이름에 AC 번호가 들어간다.

```markdown
- **AC-3**
  - Given 이미 답한 문항
  - When 같은 문항에 다시 답을 제출하면
  - Then 409를 받는다
```

- Then에는 **관찰 가능한 결과**만: 받는 상태 코드, 바뀐 상태, 보이는/안 보이는 데이터
- 정상 흐름 + 입력 오류 + 권한(남의 리소스) + 상태 충돌을 빠짐없이 본다
- 숫자 규칙(최소 개수, 최대 길이, 문항 수)은 반드시 AC로 하나씩

## spec.md에 쓰지 않는 것

테이블·컬럼, 클래스명, 라이브러리, 엔드포인트 경로, JSON 필드 구조. 이건 plan.md와 openapi.yaml에 쓴다. 섞이면 기획·프론트가 리뷰하기 어려워지고, 기술 변경 때마다 스펙을 고쳐야 한다.
(예외: 상태 코드와 ErrorCode 이름은 AC에 써도 된다 — 프론트와 합의할 관찰 결과이기 때문이다.)

## 열린 질문 다루기

- 추측 대신 질문으로 남긴다. 제안이 있으면 "(제안: ...)"을 붙인다.
- 질문이 결정되면: 본문(FR/AC/범위 밖)에 반영 → 질문 삭제. 결정 이유가 중요하면 plan.md 설계 결정(ADR)에 남긴다.

## 상태

`Draft`로만 쓴다. `Approved`는 사용자(팀)가 리뷰 후 바꾼다.

## 용어

`glossary.md`의 단어를 쓴다. 화면 문구와 코드 이름이 다르면 용어집 표에 둘 다 있는지 확인한다.
